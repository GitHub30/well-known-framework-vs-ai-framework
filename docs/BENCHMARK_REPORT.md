同一仕様・同一UI・同一SQLiteスキーマ・同一71件シードデータで実装したGoogle Driveクローン「CloudDrive」を用い、4つのPHPフレームワーク実装のパフォーマンス・メモリ効率・リクエスト内部負荷・Lighthouse品質を厳密な分離環境で比較検証した結果レポートです。

## 2. 計測環境と公平性プロトコル

### ハードウェア・ミドルウェア構成

- **OS / CPU / メモリ**: Linux 6.18.57 (x64) / Intel(R) Xeon(R) CPU @ 2.30GHz (2 vCPU) / 7.77 GB RAM
- **PHP**: PHP 8.3.6 (PHP-FPM)
- **Webサーバー**: Nginx 1.24.0（全4アプリ同一設定・gzip有効・静的キャッシュ同一・`access_log off`）
- **データベース**: SQLite 3.45.1（WALモード、`PRAGMA foreign_keys = ON`、`PRAGMA busy_timeout = 5000`、`PRAGMA synchronous = NORMAL` を全4アプリで統一）
- **PHP-FPMプール設定**: `pm = static`, `pm.max_children = 4`, `pm.max_requests = 0`
- **OPcache設定**: `opcache.enable = 1`, `opcache.memory_consumption = 256`, `opcache.interned_strings_buffer = 16`, `opcache.max_accelerated_files = 20000`, `opcache.validate_timestamps = 0`

### 公平性・分離計測プロトコル

敵対的公平性監査（[ADVERSARIAL_REVIEW.md](ADVERSARIAL_REVIEW.md)）の指摘をすべて解消したうえで、以下の手順で計測しています（生データ: [benchmark-results.json](benchmark-results.json)、計測スクリプト: [tests/benchmark.mjs](../tests/benchmark.mjs)）。

1. **完全分離実行**: 計測中は対象1フレームワークのPHP-FPMプールのみを起動し、残り3プールを停止することでCPU・メモリ・I/O競合をゼロ化。
2. **同一DB状態**: 各フレームワーク計測直前に同一のシードスクリプト（71アイテム・実ファイル群）でSQLiteを再生成。
3. **Laravelの本番同等最適化**: `composer install --no-dev --optimize-autoloader --classmap-authoritative`、`artisan optimize`（設定・ルート・イベント・Bladeビュー事前キャッシュ）、不要なステートフルセッション暗号化・ワイルドカードCORSミドルウェアを除去したステートレス構成、および他3フレームワークと同等の `DB::select()` 直接SQLクエリを適用。
4. **バイト完全一致のレスポンス**: 全4フレームワークが同一のUTF-8非エスケープJSON・同一セキュリティヘッダ・同一CSRF保護を出力することを事前検証済み。
5. **ループバック圧縮バイアス除去**: 本番Nginxはブラウザ/Lighthouse向けにgzipを有効化しつつ、`wrk` 計測時は `Accept-Encoding` を送らないことでNginx圧縮CPUによる頭打ちを防ぎ、PHP-FPM側のフレームワーク処理差を正確に抽出。
6. **反復計測**: 各シナリオでウォームアップ後に3回の本計測を実施し、スループット中央値（および対応するHdrHistogramパーセンタイル）を採用。全24計測組み合わせ（4 FW × 6シナリオ × 3回 = 72本計測）すべてで **HTTP/ソケットエラー 0 件**。

## 7. 技術的考察とトレードオフ分析

### 1. なぜAI自作フレームワークが全6シナリオで最速だったのか

- **O(1) 静的ルートディスパッチ + 最小オブジェクト生成**: PSR-7のイミュータブルストリーム/ヘッダ群や大規模DIコンテナを介さず、静的配列ハッシュ参照と軽量な `Request`/`Response` で処理するため、`/api/health` で **626 µs（2,116 req/s）** を達成。
- **最小フットプリント**: 外部依存0、1リクエストあたり15–20ファイル・606 KB `emalloc`・FPM総RSS 81 MB。
- **トレードオフ**: セキュリティ（CSRF・XSS・アップロード隔離・ヘッダ・例外処理・入力型検証）とHTTP仕様準拠（`HEAD`・`405 Allow`・末尾スラッシュ）を自前実装する必要があるため、今回の敵対的レビューのように厳格な監査とテストが不可欠。

### 2. なぜPHP 8.3 + OPcache環境で Slim 4（純PHP）が Phalcon 5（C拡張）を上回ったのか

直感に反する興味深い結果ですが、プロファイリングにより明確な構造要因が確認できました。

- **PHP 8.3 + OPcacheの進化**: `validate_timestamps=0` のOPcache下ではPHP 8.3のバイトコード実行とクラスローディングが極めて高速化されており、Slim 4の87–92ファイルはすべて共有メモリ上から即座に実行されます。さらにSlim 4は **FastRouteの結合正規表現キャッシュ（`storage/cache/routes.php`）** によりルーティングを高速化しています。
- **Phalcon 5のMVC/ルーティング/C境界オーバーヘッド**: Phalcon 5はリクエストごとに読込PHPファイル数を **6–10ファイル** まで極小化できる反面、`Phalcon\Mvc\Router` の28ルート登録＋走査だけで単体 **約155 µs**（`FactoryDefault` 生成約10 µs）、さらにZephir生成CコードからZend Engine間のプロパティ・メソッド・イベントディスパッチが積み重なり、`/api/health` で **1,204 µs** となりました。また、1,537クラスを内包する `phalcon.so` によりFPMプール総RSSは **143.74 MB** と4製品中最大でした。
- それでもPhalcon 5はLaravel 13比で **2.19x〜3.77x** 高速であり、フルスタックMVC構成としての地力は健在です（より極限まで削るなら `Phalcon\Mvc\Micro` + 最小 `Phalcon\Di\Di` という選択肢もあります）。

### 3. Laravel 13の位置づけと現実的な評価

- **シェアードナッシングPHP-FPMでの起動コスト**: 本番キャッシュ（`artisan optimize`）、権威的クラスマップ、ステートレス最小ミドルウェア、直接 `DB::select()` クエリという最大限の公平チューニングを施しても、1リクエストあたり **453–489ファイル** をロードしてServiceProvider群を起動するため、最小エンドポイントでも **5.57 ms（334 req/s）** のベースラインコストが発生します。
- **I/O支配ワークロードでの差の縮小**: 軽量API（`/api/health`）ではAI自作FWと **6.33倍** の差がつきましたが、SQLite WAL書き込みを含む `PATCH /api/items/6` では **3.26倍** に縮小しました。外部RDBMS・ネットワーク・ストレージI/Oが増える実システムではこの比率はさらに縮まります。
- **長期常駐ランタイム（Laravel Octane）という解決策**: 本計測は4フレームワーク共通の **PHP-FPM** 条件下ですが、Laravelには起動コストを初回1回に集約する **Laravel Octane（FrankenPHP / Swoole / RoadRunner）** が公式に存在します。PHP-FPM前提の単純比較と、Octane利用時の運用特性は分けて評価すべきです。
- **生産性・エコシステム**: 認証、キュー、スケジューラ、通知、テスト基盤、セキュリティアップデートの継続供給まで含めたチーム開発生産性ではLaravelが圧倒的な強みを持ちます。

### 4. まとめ：選定指針

- **超低レイテンシ・最小メモリ・依存ゼロ最優先（特定用途・エッジ/マイクロサービス）**: 自作最小FW（ただし厳格なセキュリティ監査・回帰テストが前提）
- **標準PSR互換・軽量高速・保守性のバランス最優先**: **Slim 4**（AI自作FWの71–84%の速度をPSR-7/15標準とわずか0.67 MBの `vendor/` で実現）
- **C拡張フルスタックMVC・PHPファイル数最小化**: **Phalcon 5**（導入環境でC拡張ビルド/保守が可能な場合）
- **大規模チーム開発・豊富な公式エコシステム最優先**: **Laravel 13**（高トラフィック時はOctane併用を推奨）
